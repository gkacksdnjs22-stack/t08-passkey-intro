# T08 · 공개 소개와 패스키 비공개 노트

T01의 소개, 학습 내용, 작업물, 영상, 공개 범위와 접근성 기능을 유지하고 `/private`에 패스키로 여는 개인 노트를 추가했습니다.

QR 버튼을 누르면 가운데 팝업으로 QR을 표시합니다. 배경은 어둡게 처리하고 팝업 안으로 키보드 초점을 제한합니다. 닫기·연결 취소·바깥 영역 클릭·Esc는 QR 연결을 취소합니다. 휴대폰 인증이 성공하면 팝업이 닫히고 PC의 비공개 공간이 열립니다.

결과물: https://t01-chanwon-network-intro.gkacksdnjs22.chatgpt.site/

2026-10-14 기준: 구현·TypeScript 검사·프로덕션 빌드·로컬 Worker API 검사 28개를 마쳤습니다. 검사는 메모리 안에서 만든 **소프트웨어 인증기**를 사용했습니다. Bitwarden 경로의 별도 공개키·서명·삭제 검증도 포함합니다. 실제 Bitwarden 확장에 로그인하거나 실제 보관함에 키를 저장한 검사라고 주장하지 않습니다. 학생의 실제 기기 등록·저장 위치 확인·실제 사용 완료를 대신하지 않습니다. ALEPH에 제출하거나 과제 완료를 표시하지 않았습니다.

## ① 무엇으로 붙였나

WebAuthn 라이브러리 `@simplewebauthn/server 14.0.3`와 `@simplewebauthn/browser 14.0.0`으로 구현했습니다. Cloudflare D1에 계정·COSE 공개키·일회용 challenge·세션 해시·비공개 노트를 저장합니다. 사이트에는 비밀번호 입력란이 없고 OTP나 별도 OAuth 로그인으로 패스키를 대체하지 않습니다. 플랫폼의 공개 접근 설정을 유지합니다.

## ② 왜 그걸 골랐나

학생은 **휴대폰 지문 패스키와 Bitwarden에 저장하는 별도 예비 패스키**를 선택했습니다. 휴대폰 방식은 PC에서 WebAuthn을 호출하지 않습니다. 사이트가 5분짜리 일회용 QR을 표시하고, 휴대폰 카메라로 스캔하면 같은 사이트의 `/phone-connect`가 열립니다. WebAuthn 등록·서명은 휴대폰에서 실행하며 `localDevice`/`client-device`로 휴대폰 인증을 안내하고 UV를 필수로 검증합니다. 지문 확인은 휴대폰에서 처리됩니다. 기기 설정에 따라 얼굴·PIN도 제공될 수 있으며, 서버는 지문이라는 생체 방식만을 강제하거나 지문 원본을 받지 않습니다. 이 연결은 사이트의 일회용 QR을 사용하는 구조로 Bluetooth 페어링은 필요 없고 PC·휴대폰의 인터넷 연결이 필요합니다.

예비 키는 Bitwarden 확장이 설치된 Chrome·Edge에서 별도로 생성합니다. 로그인한 계정에만 키 추가를 허용하고, 서버에는 첫 번째와 다른 credential ID·공개키·이름·등록일·사용자가 확인한 저장 위치를 보관합니다. 단순히 휴대폰 키를 동기화한 것을 두 번째 키로 세지 않습니다. Bitwarden 경로는 휴대폰 연결용 hybrid 힌트나 특정 기기 attachment를 강제하지 않으며, 서버의 UV·origin·RP ID·서명 검증은 동일하게 유지합니다. 예비 키 로그인에는 이 계정에서 Bitwarden으로 표시한 활성 키만 허용합니다.

Bitwarden 보관함 비밀번호와 이메일 2단계 인증은 Bitwarden에서 처리하고 우리 사이트는 받지 않습니다. 휴대폰을 잃어도 관리자 비밀번호를 기억하고 등록한 이메일에 접근할 수 있다면 Bitwarden에 다시 로그인해 미리 등록한 예비 키를 사용할 수 있습니다. 관리자 비밀번호까지 잊은 상황을 이메일만으로 복구할 수 있다고 주장하지 않습니다. 우리 사이트에는 비밀번호·이메일 코드 입력칸이 없습니다. 이는 과제의 공개키 서명 검증과 사이트 비밀번호 입력칸 금지에 근거한 구현입니다.

Bitwarden 확장이 응답하면 확장 자체 화면에서 저장·인증을 진행합니다. 웹사이트가 특정 확장의 설치·활성 상태를 보장하거나 네이티브 브라우저 화면을 완전히 차단할 수는 없습니다. 준비 확인을 체크해야 버튼이 활성화되며, 확장이 없거나 응답하지 않으면 Windows 보안창으로 넘어갈 수 있음을 안내합니다. Codex 내장 브라우저의 Bitwarden 확장 지원은 확인하지 못했으므로 실제 사용은 지원되는 Chrome·Edge에서 확인해야 합니다.

QR에 담긴 256비트 무작위 연결 값은 URL의 fragment에만 넣어 일반 페이지 요청·리퍼러에 포함되지 않게 합니다. DB에는 연결 값과 PC 쿠키의 해시만 저장합니다. 휴대폰이 정상 패스키 서명을 완료하면 서버가 연결을 승인 대기로 바꾸고, 원래 PC의 HttpOnly 연결 쿠키와 일치할 때만 일회용 연결을 소비해 세션을 발급합니다. 다른 PC, 인증 전 소비, 재사용, 취소된 QR은 거절됩니다. 기존 계정에 예비 키를 추가하는 QR은 원래 PC의 살아 있는 로그인 세션에 묶입니다.

인증 서명·origin·RP ID·기기 본인확인 검증은 검증된 라이브러리에 맡겼습니다. 직접 암호·CBOR 검증기를 작성하는 방법은 구현 실수 가능성을 줄이기 위해 고르지 않았습니다. OTP는 공개키 저장·패스키 삭제·서명 검증 요구사항을 대신할 수 없어 선택하지 않았습니다.

공식 문서: https://simplewebauthn.dev/docs/packages/server , https://simplewebauthn.dev/docs/packages/browser

Bitwarden 공식 문서: https://bitwarden.com/help/storing-passkeys/ , https://bitwarden.com/help/setup-two-step-login-email/

## ③ 어디를 어떻게 고쳤나

- `app/page.tsx`: 기존 공개 소개를 유지하고 비공개 공간 링크를 추가했습니다.
- `components/private-space.tsx`, `app/private/page.tsx`: 등록·로그인·로그아웃, 노트 보기·수정, 패스키 목록·추가·삭제 확인, 모든 패스키를 잃었을 때의 안내를 구현했습니다.
- `components/private-space.tsx`의 `managerAuthenticate`: 준비 확인 후 Bitwarden 등록·로그인 WebAuthn을 호출합니다. 관리자 계정 비밀번호·메일 코드는 수집하지 않습니다.
- `components/phone-connect.tsx`, `app/phone-connect/page.tsx`: QR을 스캔한 휴대폰에서 기기 패스키 등록·지문 인증을 진행합니다.
- `app/api/phone-pair/[action]/route.ts` → `lib/passkey.ts`의 `phoneRoute`: QR 시작·정보·PC 상태 조회·일회용 소비·취소입니다. PC에서 공개키 서명을 검증하지 않고도 로그인되게 하는 우회는 없으며, 휴대폰의 WebAuthn 검증 성공을 요구합니다.
- `app/api/passkey/[action]/route.ts` → `lib/passkey.ts`: `register-options`/`register-verify`, `login-options`/`login-verify`, `logout`, `keys`, `delete-key`, `cancel`, `session` 경로입니다.
- `app/api/private-notes/route.ts` → `lib/passkey.ts`의 `notesRoute`: 세션이 없으면 401, 남의 노트 ID는 403입니다. 조회·수정의 소유자는 클라이언트가 적은 계정이 아니라 서버 세션으로 결정합니다.
- `db/schema.ts`, `drizzle/`: 계정·패스키·challenge·세션·노트 테이블과 버전별 SQL 마이그레이션입니다. 요청 처리에서 테이블을 생성하지 않습니다.

등록: 서버가 5분짜리 무작위 질문을 발급하고 브라우저의 HttpOnly 흐름 쿠키에 묶어 저장합니다. 정상 응답 검증 뒤 공개키·credential ID·카운터·전송 방법·이름·사용자가 선택한 저장 위치를 저장합니다. 서버가 받은 등록 본문에는 공개키를 포함하는 attestationObject와 clientDataJSON이 있으며 개인키가 없습니다. 검증 실패·취소 때 신규 계정·패스키를 저장하지 않습니다. 두 번째 패스키 등록은 살아 있는 기존 세션에만 허용합니다.

로그인: 요청마다 새 질문을 발급합니다. 서버가 질문을 원자적으로 소비한 뒤 저장된 공개키로 서명, origin, RP ID, 사용자 본인확인 UV, 카운터를 검증합니다. 실패한 질문도 다시 쓸 수 없습니다. 인증 뒤 32바이트 무작위 세션을 만들고 DB에는 SHA-256 해시만 저장합니다. HTTPS 쿠키는 Secure·HttpOnly·SameSite=Strict, 최대 12시간입니다. 같은 브라우저에서 인증을 갱신하면 이전 세션을 폐기합니다.

로그아웃: DB에서 해당 세션과 진행 중 질문을 삭제하고 쿠키를 비웁니다. 기존 쿠키로 다시 자료를 요청하면 401입니다.

패스키 삭제: 본인 키인지 검사하고 `revoked_at`으로 사용 권한을 철회합니다. 목록·인증 대상에서 제외하고 그 키의 세션도 폐기합니다. 패스키 관리자에 저장된 키를 원격으로 삭제하는 기능은 아닙니다. 마지막 키를 삭제하면 계정의 노트를 다시 열 수 없으며, 다른 별명으로 신규 계정을 만드는 안내를 보여 줍니다.

## ④ 안 열리는 것을 확인한 기록

`docs/evidence/local-security-check.json`에 실행 시각, 요청 본문, HTTP 상태와 응답이 있습니다. 쿠키·세션 토큰·소프트웨어 인증기의 개인키는 기록하지 않았습니다. 이 파일의 계정과 노트는 가상 검사 자료입니다.

| 확인 | 성공 요청 | 거절 요청 |
| --- | --- | --- |
| 로그인 없이 열기 | 본인 세션의 노트 조회 200 | 미로그인 조회 401 |
| 남의 패스키·자료 | 각 계정의 패스키 로그인·본인 노트 조회 200 | 다른 계정의 키로 로그인 401, A→B 및 B→A 노트 조회 403 |
| 사용한 질문 재사용 | 새 질문에 대한 정상 서명 200 | 동일 질문·응답 재사용 401, 동시 요청 중 한 개만 200 |
| 패스키 삭제 뒤 로그인 | 남은 두 번째 키 로그인 200 | 삭제한 키 로그인 401 |

다른 계정의 자료 변경 시도 뒤 자료 건수와 내용이 그대로인 것도 검사했습니다. 다른 owner ID를 URL에 넣어도 본인 자료만 반환됩니다. 서명 변조, 다른 origin의 서명, UV 누락, 이전 세션 재사용, 등록 도중 로그아웃, 남의 패스키 삭제, 마지막 키 삭제 뒤 자료 접근도 검사했습니다.

Bitwarden 경로의 소프트웨어 인증기 검사: 미로그인 추가 거절 403, 기존 계정에 서로 다른 두 공개키 등록, 추가 요청의 별명 위조 무시, 관리자 경로에서 휴대폰 키 제출 시 401, 관리자 키의 정상 서명 성공, 같은 응답 재사용 401, 남의 노트 403, 휴대폰 키 삭제 뒤 관리자 키로 재로그인 성공을 확인했습니다.

학생이 직접 남길 확인: 실제 기기에서 첫 번째·두 번째 패스키를 등록하고 각각 저장 위치를 확인합니다. 하나 삭제 후 남은 것으로 재로그인하고, 화면의 ‘이번 확인 기록 다운로드’로 요청·응답을 보관합니다. 두 계정의 실제 기기 확인까지 끝난 뒤 최종 설명서를 갱신합니다.

## ⑤ AI와 나

AI에게 맡긴 일: 기존 소스·배포 상태 확인, 화면과 API, 데이터베이스, 자동 검사, 설명서 초안 작성.

내가 직접 판단한 일: 휴대폰 지문 패스키와 Bitwarden 예비 패스키를 선택했습니다. 휴대폰을 잃어도 다른 기기를 미리 등록하지 않고 예비 키를 쓸 수 있는 구성을 원했습니다. 비공개 노트의 세 가지 가상 분야와 구체적인 예시 문장은 AI가 정한 기본값이며 학생의 실제 기록이라고 주장하지 않습니다.

AI 제안을 따르지 않은 일: Windows Hello PIN을 예비 키로 쓰거나 다른 휴대폰을 미리 등록하는 제안을 선택하지 않았습니다. Windows 보안창을 피하고 추가 기기에 의존하지 않는 방식을 원했기 때문입니다. 실제 기기·Bitwarden 등록·사용 확인은 학생이 직접 진행해야 합니다.

## ⑥ 아직 못 막은 것

- 모든 패스키를 잃었을 때 복구할 별도 신원 확인·복구 체계가 없습니다. 노트는 삭제되지 않아도 계정 접근은 복구하지 못합니다.
- Bitwarden 관리자 계정의 접근·동기화·이메일 인증과 확장 동작은 외부 서비스에 의존합니다. 우리 사이트에서 키를 철회하면 관리자의 계정을 복구해도 그 키로 사이트에 들어올 수 없습니다. Bitwarden 저장 위치는 자기 보고로 실제 공급자를 암호학적으로 증명하지 않습니다.
- 유효한 세션이 탈취되면 만료·로그아웃 전 접근할 수 있습니다. 패스키 추가·삭제 때의 별도 재인증은 아직 붙이지 않았습니다.
- 키 추가용 QR의 연결 값을 다른 사람이 촬영하거나 전달받으면 그 PC의 로그인 권한으로 자신의 키를 추가할 수 있습니다. 연결은 5분·일회용이며 취소할 수 있지만 QR 유출 자체를 막는 별도 승인 절차는 없습니다. 자신의 PC에서 시작한 QR만 스캔하도록 휴대폰 화면에 안내합니다.
- 공개 가입·질문 발급에 대한 IP별 속도 제한과 가입 스팸 방지는 아직 없습니다.
- 사용자가 고른 저장 위치는 자기 보고이며, 서버가 패스키 관리자의 실제 보관 위치를 자동 확인한 정보가 아닙니다.
- 실제 기기·패스키 관리자·브라우저 조합의 성공 여부는 학생 확인이 남았습니다. 동기화되는 패스키의 개인키 관리는 해당 관리자의 정책을 따릅니다.

## 짧은 확인 방법 4줄

어디로 가나요: 공개 결과물의 ‘비공개 공간’ 링크를 엽니다.

세 단계 안에 무엇을 하나요: ① 휴대폰 QR로 첫 패스키를 등록·로그인 ② 로그인 상태에서 Bitwarden 확장 준비를 확인하고 예비 패스키를 별도로 등록 ③ 로그아웃 후 ‘Bitwarden 예비 키’로 같은 별명에 로그인해 노트와 패스키 두 개 확인. Bitwarden 확장 계정 로그인과 이메일 2단계 인증은 공식 안내대로 미리 설정합니다.

무엇이 보이면 통과인가요: 공개 소개는 인증 없이 보이고, 패스키 인증 뒤 본인 노트 3개와 패스키 이름·등록일이 보입니다. 추가·삭제·거절 검증은 위 확인 기록으로 판단합니다.

안 될 때는 무엇이 보이나요: 인증 취소·지원되지 않는 브라우저·접근 거절 안내가 보이고 비공개 노트는 열리지 않습니다.

## 개발과 검사

`npm ci` → `node node_modules/drizzle-kit/bin.cjs generate` → `npm run build`.

로컬 DB는 `node node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/<해당 마이그레이션>.sql`로 **아직 적용하지 않은 SQL만 순서대로** 적용합니다.

`node node_modules/wrangler/bin/wrangler.js dev --config dist/server/wrangler.json --local --persist-to .wrangler/state --ip 127.0.0.1 --port 8788 --inspector-port 0` 실행 뒤 `node tests/passkey.integration.mjs http://localhost:8788`로 검사합니다. 키와 쿠키는 프로세스 메모리에서만 만들고 검사 키는 마지막에 철회합니다. 공개 서버 검사를 실행하면 가상 검사 계정·노트가 생성되므로 학생의 실제 사용 기록과 구분합니다.

Windows 로컬 Wrangler에서는 다른 origin을 거절하는 검사 직후 첫 변경 요청이 503이 되는 실행기 현상을 확인했습니다. 그 검사를 마지막에 배치해 인증 검증과 실행기 오류를 구분했습니다. 기능의 접근 검사와 서명 검증을 약화하지 않았습니다.
